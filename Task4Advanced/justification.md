# Обоснование событийного подхода

## Проблема текущего состояния

- Вся интеграция идёт через Camel ESB и DWH SQL Server 2008: любое новое требование превращается в ещё одну
  трансформацию и ещё одну хранимую процедуру в DWH.
- Отчёты строятся часами, потому что аналитика, транзакционная логика и интеграции соревнуются за один ресурс.
- Новый бизнес (фарма-партнёры, производитель электроники, новые регионы) подключается через изменение DWH —
  это противоречит требованию «без значительных объёмов бизнес-логики в DWH».
- Платформа SQL Server 2008 вне поддержки вендора (риск безопасности и соответствия).

## Сравнение подходов

| Критерий | Camel ESB + DWH (сейчас) | Событийная платформа (цель) |
|---|---|---|
| Связность | Точечные синхронные интеграции, высокая связность через центральную шину | Домены публикуют факты и не знают подписчиков; слабая связность |
| Подключение нового источника | Новая трансформация в шине + изменения DWH; недели | Новый продюсер публикует событие по контракту; консьюмеры подписываются сами; дни |
| Масштабирование | Вертикальное (один SQL Server, одна шина) | Горизонтальное: партиции, независимое масштабирование доменов |
| Скорость данных | Пакетная выгрузка, отчёты часами | Near-real-time потоковые витрины, цель ≤ 60 с |
| Отказоустойчивость | Сбой шины или DWH останавливает всё | Сбой консьюмера не влияет на продюсера; сообщения буферизуются, DLQ |
| Бизнес-логика | В DWH и шине | В доменах; DWH/Camel — только мосты |
| Аудит и история | Только текущее состояние в таблицах | Журнал событий: расследования, сверка, повторные расчёты |
| Данные для аналитики | Копии таблиц, длинные ETL | Data products с контрактом, владельцем и SLA |
| Регуляторика | Доступ на уровне БД, трудно локализовать | Политики по топикам и доменам, раздельные контуры, события без медицинских данных и без прямых персональных данных — только идентификаторы и факты |
| Региональное расширение | Копия DWH или общий мегабазис | Региональные кластеры, маршрутизация по резидентности |

## Преимущества для «Будущего 2.0»

1. **Гибкость.** Новые направления (кредитование, аптека, партнёры) добавляются как новые домены без
   переписывания существующих. Подписка на уже публикуемое событие не требует изменений продюсера.
2. **Масштабируемость.** Топики разбиваются по ключу агрегата, нагрузка растёт линейно; ресурсы доменов
   изолированы в облаке, что совпадает с планом отдельных сред.
3. **Скорость реакции.** «Платёж получен» немедленно закрывает счёт, «Пройдено исследование» запускает ИИ-анализ,
   «Остаток ниже порога» — закупку, без ожидания ночной загрузки.
4. **Аналитика без нагрузки на транзакционный контур.** Потоковые витрины и портал самообслуживания читают
   data products, а не операционные базы; время построения отчёта падает с часов до секунд-минут.
5. **Монетизация ИИ.** Событие `ai.analysis.completed` — готовая точка учёта использования и тарификации.
6. **Безопасность по построению.** Контракты событий не содержат медицинского содержимого; запрет на уровне
   схемы проще проверить и аудировать, чем права на таблицы DWH.
7. **Эволюционная миграция.** CDC и ACL-адаптеры позволяют переносить домены по одному (Strangler Fig), не
   останавливая бизнес.

## Компромиссы и как мы с ними работаем

| Недостаток | Мера |
|---|---|
| Итоговая согласованность вместо ACID между доменами | Саги и компенсирующие события; транзакционный outbox; критичные операции остаются внутри одного агрегата |
| Сложнее отлаживать цепочки | `correlation_id`, распределённая трассировка, lineage |
| Эволюция схем | Schema Registry, обратная совместимость, контрактные тесты |
| Дубли и порядок | Идемпотентные консьюмеры, партиционирование по ключу агрегата |
| Операционная сложность Kafka | Управляемый сервис, SRE-команда, SLO по лагу |
| Не всё подходит под события | Запросы «в реальном времени» с немедленным ответом остаются синхронными внутри домена |

## Целевые показатели эксплуатации

Компромиссы выше — не «сложнее, и всё»: у каждого есть измеримая цель. Показатели проверяются на
пилоте (месяцы 0–6), затем закрепляются в SLA платформы; в контрольные точки этапов роадмапа попадают ключевые из них —
время отчёта и лаг потоковых витрин (`../Task5Advanced/roadmap.md`, этап 2).

| Показатель | Цель | Как измеряем | Что будет при нарушении |
|---|---|---|---|
| Разбор DLQ | ≤ 4 часа (p95), 100% сообщений разобраны в SLA | Возраст старейшего сообщения в `<topic>.dlq`, алерт через 30 минут | Дежурный SRE, runbook, эскалация владельцу домена |
| Доля событий в DLQ | ≤ 0,1% от трафика | Счётчики групп потребителей (consumer group) и DLQ-топика | Блокирует релиз консьюмера, разбор причин |
| Лаг консьюмера (near-real-time) | целевой ≤ 60 с (p50), предельный ≤ 5 минут (p95) | Kafka consumer lag, OpenTelemetry | Алерт, автоскейл консьюмеров, остановка деплоя продюсера |
| Лаг batch-витрин | ≤ 4 часа | Показатель свежести data product | Инцидент качества данных, уведомление владельца |
| Повторная обработка | ≤ 0,5% событий; побочных эффектов от дублей — 0 | Метрика retry, тесты идемпотентности | Расследование, правка консьюмера |
| Потеря событий | 0 (at-least-once + outbox); RPO ≤ 1 минута | Сверка outbox и Kafka, reconciliation | Инцидент P1, восстановление из outbox |
| Сломанные контракты в проде | 0 | Schema Registry + контрактные тесты в CI | Merge блокируется |
| Время реакции на инцидент (P1) | MTTR ≤ 1 час | Инцидент-трекинг, трассировка | Постмортем, пересмотр SLO |
| Полнота трассировки | ≥ 95% событий с `correlation_id` | Grafana/Tempo | Разбор цепочек замедляется — правим инструментирование |
| p95 отчёта в портале | ≤ 30 с на пилоте, ≤ 3 с после предагрегатов | APM портала | Оптимизация витрин, cost guard |
| Соблюдение SLA свежести data products | ≥ 95% продуктов | Каталог и мониторинг свежести | Штрафной флаг в каталоге, ревью с владельцем |

Именно эти цифры отвечают на вопрос «насколько сложнее отлаживать»: сложность компенсируется
трассировкой (`correlation_id`/`causation_id`, lineage), а не «героическим разбором логов».

## Что не меняем сразу

Camel ESB и DWH остаются мостами совместимости (по постановке бизнеса): через ACL-адаптеры они преобразуют
легаси-форматы в канонические события. Отказ от синхронных интеграций на критическом пути — этап 18–36 месяцев.

|---|---|
| Через год: портал самообслуживания | Data products собираются из событий, портал не зависит от DWH |

| Новые регионы | Региональные контуры, одинаковые контракты |
| От batch к near-real-time | Потоковые витрины как штатный способ публикации данных |
| Слабосвязанная событийная платформа через 3 года | Прямой целевой паттерн; Camel и DWH — только мосты |
