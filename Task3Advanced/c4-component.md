# C4 — уровень компонентов

Внутреннее устройство ключевых контейнеров целевой архитектуры «Будущего 2.0». Контекст —
[`c4-context.md`](c4-context.md), контейнеры и их эволюция — [`c4-container.md`](c4-container.md),
карта рисков — [`risk-map.md`](risk-map.md), план управления — [`risk-management-plan.md`](risk-management-plan.md).

Раскрыты три области: **портал самообслуживания**, **Event Platform** и **доменный сервис Billing &
Settlement** как пример устройства любого домена (шаблон домена — раздел 3).

**Диаграммы:** [`c4-component.drawio`](c4-component.drawio) — страницы «Компоненты — Портал»,
«Компоненты — Event Platform» и «Компоненты — Billing & Settlement». draw.io — редактируемый исходник
диаграмм, разделы 1–4 — их текстовое описание: состав компонентов, ответственность и связи. В draw.io
синие блоки — компоненты контейнера, жёлтые — внешние контейнеры, серые — легаси-мосты, пунктирная
рамка — граница контейнера. Асинхронные потоки идут через Event Platform; синхронные вызовы
допускаются только внутри домена.

## 1. Портал самообслуживания

### 1.1. Назначение и границы

Портал даёт сотруднику головного офиса и BI-аналитику самообслуживание по данным: найти
опубликованный data product и его владельца, SLA, контракт и качество; получить отчёт по своему
срезу в пределах уровня доступа; собрать собственный отчёт без BI-команды; выгрузить результат, если
это разрешено политикой и зафиксировано в аудите. BI-аналитик публикует сертифицированные метрики и
описания витрин через семантический слой и каталог; физическая публикация data product — задача
доменного Data Product Publisher.

Портал не источник истины: он читает только опубликованные data products из lakehouse, прямые запросы
к DWH, доменным БД и клиническому контуру запрещены. Power BI сохраняется для регламентных отчётов и
работает на тех же data products.

### 1.2. Компоненты

| Компонент               | Ответственность                                                                                                              | Технология и интерфейсы                                                                                   | Ключевые правила и ограничения                                                                                                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Web UI**              | Каталог data products, конструктор отчётов, просмотр, экспорт; отображение только доступных ресурсов                         | React + TypeScript; REST/JSON через BFF; OIDC-сессия                                                      | Не граница безопасности: скрывает недоступное, решение о доступе принимает AuthZ. В БД не ходит                                                                                                    |
| **BFF / API Gateway**   | Оркестрация запросов UI, агрегация ответов, rate limit, correlation ID, аудит обращений; доменной логики не содержит         | Go; REST/JSON; OIDC/JWT; вызовы AuthZ, Catalog Client, конструктора, Audit & Consent                      | Каждый запрос проходит AuthZ. Лимиты на пользователя и тенанта. В DWH и чужие БД не обращается                                                                                                     |
| **AuthZ Gateway**       | Точка исполнения политик (PEP): проверка токена, сбор атрибутов, вызов внешнего движка решений, применение row-level filters | Go; OPA-клиент + JWT; решение ABAC принимает внешний контейнер «IDP + Policy Engine»; краткий кэш решений | Deny by default. Медицинские scope запрещены безусловно. Решение и факт проверки аудируются. Закрывает риск S4                                                                                     |
| **Catalog Client**      | Поиск и карточки data products: владелец, SLA, контракт, качество, происхождение; фильтрация закрытого контура               | Go; DataHub GraphQL; кэш метаданных                                                                       | Возвращает только опубликованные data products. Медицинские и закрытые ресурсы отфильтровываются. Данные не читает                                                                                 |
| **Конструктор отчётов** | Сборка отчёта из измерений и метрик, фильтры, шаблоны, спецификация, экспорт                                                 | React/TypeScript + JSON-спецификация; JSON Schema-валидация; вызовы семантического слоя через BFF         | Произвольный SQL не пишется. Доступны только сертифицированные метрики и разрешённые срезы. Спецификации версионируются                                                                            |
| **Семантический слой**  | Единые определения метрик, связей, row-level filters и предагрегатов; публикация сертифицированных метрик                    | dbt-метрики + Cube.js; REST/GraphQL; формирует SQL для Query Service                                      | У каждой метрики есть владелец, метрики сертифицированы. Фильтры доступа подставляются до выполнения запроса. Единая точка определения метрик — иначе растут противоречивые «отчётные» определения |
| **Query Service**       | Выполнение запросов к lakehouse через Trino; cost guard, таймауты, лимиты параллелизма и объёма результата; журнал запросов  | Go-клиент Trino; SQL; Arrow/JSON; квоты на тенанта                                                        | Принимает только SQL семантического слоя. В DWH не подключается. Защищает от «бутылочного горлышка» (A5) и роста стоимости (T1)                                                                    |
| **Audit & Consent**     | Append-only журнал доступа, запросов и экспорта; фиксация проверки согласия; алерты; хранение по политике                    | Go + PostgreSQL; асинхронные события; выгрузка в «Наблюдаемость и lineage»                                | Источник согласия — Identity & Access; компонент фиксирует факт проверки, а не владеет согласием. Медданные в журнал не пишутся. Журнал неизменяем                                                 |

Внешние элементы: **IDP + Policy Engine** (Keycloak + OPA) — аутентификация и решения ABAC;
**Каталог данных и схем** (DataHub) — метаданные и политики; **Data Platform (lakehouse)** —
аналитическое хранилище; **Наблюдаемость и lineage** — аудит, алерты и трассировка.

### 1.3. Взаимодействие компонентов

Схема: [`c4-component.drawio`](c4-component.drawio), страница «Компоненты — Портал».

1. Пользователь проходит OIDC-аутентификацию в IDP; Web UI получает токен.
2. Web UI отправляет запрос в BFF, тот — в AuthZ Gateway.
3. AuthZ Gateway проверяет токен и запрашивает решение ABAC по атрибутам «пользователь — роль — домен —
   data product — цель»; возвращает разрешение и row-level filters.
4. Для поиска ресурса BFF вызывает Catalog Client; тот читает метаданные из DataHub по GraphQL. Закрытые
   и медицинские ресурсы в выдачу не попадают.
5. Для отчёта BFF вызывает конструктор; спецификация проверяется и передаётся в семантический слой.
6. Семантический слой подставляет разрешённые метрики и фильтры и формирует SQL; Query Service
   выполняет его в Trino с учётом квот и cost guard.
7. BFF и Catalog Client пишут события доступа в Audit & Consent; экспорт дополнительно проверяется
   политикой и фиксируется в журнале.

### 1.4. Исключение медицинских данных: защита в глубину

Требование «в витрину не попадают медкарты, истории болезней и результаты исследований» выполнено не
одним запретом, а независимыми барьерами — каждый из них реализован конкретным компонентом портала:

| Барьер       | Компонент и механизм                                                                                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Источник** | Medical Record — закрытый контур: медсодержимое не публикуется в Event Platform, lakehouse и каталог, поэтому не становится data product                                                       |
| **Каталог**  | Медицинские активы помечены в DataHub как закрытые, Catalog Client отфильтровывает их из поиска и карточек; CI-тест падает, если в каталоге появится data product с PII-тегом `medical_record` |
| **Доступ**   | AuthZ Gateway применяет deny-правило OPA к медицинским scope и ресурсам — отказ до обращения к данным, а не после загрузки страницы                                                            |
| **Запрос**   | Query Service подключается только к аналитическому lakehouse, куда медицинские данные не загружаются; у портала нет учётных данных DWH или доменных БД                                         |
| **Аудит**    | Попытки обращения к закрытым ресурсам и экспорт чувствительных выборок фиксируются в Audit & Consent и выгружаются в «Наблюдаемость и lineage»                                                 |

Ошибка в одном слое не открывает медицинские данные в портале — это закрывает риск S1. Три меры S1 из
[`risk-management-plan.md`](risk-management-plan.md) (данные вне контура, deny-политика OPA, CI-тест на
PII-тег) закрыты барьерами «Источник», «Доступ» и «Каталог» соответственно; «Запрос» и «Аудит» — их
дополнение. Разрешённые для аналитики клинические факты (идентификаторы и факты потоков) могут быть
data products; медкарты, истории болезней и результаты исследований — нет.

### 1.5. SLO и контроль

| Показатель                       | Целевое значение              | Как контролируется                                         |
| -------------------------------- | ----------------------------- | ---------------------------------------------------------- |
| Интерактивный отчёт в портале v1 | p95 ≤ 3 с                     | предагрегаты Cube.js, запросы только к витринам            |
| Прототип портала на этапе 1      | p95 ≤ 30 с                    | ограниченный набор data products и пилотных пользователей  |

| Доступ                           | 100% запросов через AuthZ     | аудит, тесты политик, запрет обхода BFF                    |

## 2. Event Platform

### 2.1. Назначение и границы

Event Platform — слабосвязанная событийная шина доменов: публикация доменных фактов, доставка
подписчикам, CDC из легаси-DWH, доставка данных в lakehouse. Платформа не содержит бизнес-логики
доменов: синхронные вызовы допускаются только внутри домена, между доменами — события. Camel ESB и
DWH SQL Server 2008 подключаются только как «мосты совместимости» и выводятся из критического пути
к 36-му месяцу.

### 2.2. Компоненты

| Компонент            | Ответственность                                                                                                                                    | Технология                                                                   | Ключевые правила                                                                                                                                                                                                              |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Schema Registry**  | Хранение и версионирование схем событий, проверка совместимости, выдача schema id                                                                  | Confluent Schema Registry / Apicurio                                         | `event_version` — версия схемы payload; суффикс топика `.v1`/`.v2` — мажорная версия контракта: обратно совместимые добавления остаются в `.v1`, ломающее изменение — новый топик `.v2`. Несовместимая схема отклоняется в CI |
| **Event Governance** | Владельцы топиков, классификация PII, retention, именование по `<контекст>.<агрегат>.<факт в прошедшем времени>`, жизненный цикл, политики доступа | OPA + DataHub (внешний каталог)                                              | У каждого топика есть владелец и контракт. Медицинское содержимое запрещено. Retention и PII-политики проверяются автоматически, изменения аудируются                                                                         |
| **Kafka Brokers**    | Долговременный журнал событий, партиционирование, репликация, доставка подписчикам                                                                 | Kafka 3.x; RF=3, `min.insync.replicas=2`; идемпотентный продюсер, `acks=all` | Порядок гарантируется только в пределах ключа партиции (ID агрегата), глобального порядка нет. Критичные топики получают региональную репликацию                                                                              |
| **Outbox Relay**     | Атомарная публикация: запись в БД и событие не расходятся; повторная отправка после сбоя                                                           | Go sidecar; таблица outbox в БД домена                                       | Разворачивается рядом с доменным сервисом, на схеме показан как общий механизм Event Platform. At-least-once; повтор безопасен благодаря `event_id` и идемпотентным консьюмерам. Dual-write запрещён                          |
| **DLQ Manager**      | Изоляция «ядовитых» сообщений, повторные попытки, воспроизведение после исправления, алерты                                                        | Kafka + Go                                                                   | DLQ на группу потребителей; сообщения не удаляются молча. Разбор ≤ 4 ч p95, доля DLQ ≤ 0,1% трафика. Воспроизведение — после исправления и с идемпотентной проверкой                                                          |
| **Kafka Connect**    | CDC из DWH, доставка событий и data products в lakehouse, sink-коннекторы                                                                          | Debezium + sink-коннекторы                                                   | CDC только читает легаси-источник, новой бизнес-логики в DWH не появляется. Запись в Iceberg идемпотентна по ключу, схемы маппятся в канонический формат                                                                      |
| **ACL Adapters**     | Перевод легаси-сообщений Camel и структур DWH в канонические доменные события                                                                      | Camel / Go                                                                   | Anti-corruption layer: легаси-модель не протекает в домены. Маппинг версионируется, ошибки видны в мониторинге. Адаптер временный и удаляется после вывода источника                                                          |

Внешние элементы: **доменный сервис-продюсер** и **доменный сервис-подписчик** (общение только через
события), **Camel ESB** и **DWH SQL Server 2008** (легаси-мосты), **Device Telemetry Gateway**
(MQTT → Kafka) — дополнительный источник, **Каталог данных и схем** (DataHub) — реестр владельцев,
**Data Platform (lakehouse)**, **Портал самообслуживания**, **Наблюдаемость и lineage**.

### 2.3. Потоки и гарантии доставки

Схема: [`c4-component.drawio`](c4-component.drawio), страница «Компоненты — Event Platform».

1. Доменный сервис пишет изменение и событие в outbox в одной транзакции.
2. Outbox Relay публикует событие в Kafka; схема регистрируется или проверяется в Schema Registry.
3. Подписчик читает событие, проверяет `event_id` и обрабатывает его идемпотентно.
4. При ошибке выполняются повторные попытки; после исчерпания сообщение уходит в DLQ.
5. Дежурный разбирает DLQ, исправляет консьюмер и воспроизводит сообщения — потеря не допускается.
6. Kafka Connect доставляет поток в lakehouse, OpenLineage фиксирует происхождение и лаг.
7. Camel и DWH подключаются через ACL Adapters/CDC только как мосты; новые домены их не используют.

| Свойство           | Значение                         | Механизм                                                             |
| ------------------ | -------------------------------- | -------------------------------------------------------------------- |
| Доставка           | At-least-once                    | outbox + повторная публикация, идемпотентный консьюмер по `event_id` |
| Потеря событий     | 0, RPO ≤ 1 мин                   | `acks=all`, RF=3, `min.insync.replicas=2`, сверка outbox и Kafka     |
| Порядок            | только в пределах ключа партиции | ключ — ID агрегата; глобальный порядок не обещается                  |
| Лаг near-real-time | ≤ 60 с p50, ≤ 5 мин p95          | партиции, автоскейл консьюмеров, алерты по consumer lag              |
| DLQ                | ≤ 0,1% трафика; разбор ≤ 4 ч p95 | DLQ Manager, runbook, владелец домена                                |

## 3. Общий шаблон доменного сервиса

Каждый доменный сервис устроен по одному шаблону — это снижает стоимость подключения нового
направления и делает поведение доменов предсказуемым. Шаблон не означает общую модель данных: у каждого
домена свои агрегаты, своя БД и свои контракты.

| Компонент                  | Обязательность             | Обязанность и правила                                                                                                                                                                                |
| -------------------------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Domain API**             | Обязательный               | Синхронные команды и запросы для пользователей и систем **внутри домена**: OpenAPI/gRPC-контракт, идемпотентные команды по ключу, авторизация через OPA. Чужие БД не читает                          |
| **Domain Model**           | Обязательный               | Агрегаты, инварианты, доменные политики и расчёты. Один агрегат — одна транзакционная граница; кросс-доменные сценарии — саги, а не общая транзакция                                                 |
| **Domain Store**           | Обязательный               | Собственная БД домена: агрегаты, outbox, проекции. Пишет только домен, прямых чтений чужих таблиц нет. PITR, шифрование, резервное копирование                                                       |
| **Outbox + Publisher**     | Обязательный               | Публикация доменных событий с гарантией доставки: запись в БД и событие — в одной транзакции, at-least-once, `event_id` UUIDv7, порядок по ключу агрегата                                            |
| **Event Handlers**         | Обязательный при подписках | Реакция на события других доменов: идемпотентность по `event_id`, дедупликация, повторные попытки, DLQ. Только события и API, не прямые чтения                                                       |
| **Process Manager / Saga** | Опциональный               | Длительный кросс-доменный процесс и компенсации: состояние — в домене-координаторе, компенсирующие события идемпотентны, общей транзакцией домены не блокируются                                     |
| **Read Models**            | Опциональный               | Проекции для запросов и отчётов домена: строятся из событий или своего стора, источником истины не являются, пересобираемы                                                                           |
| **Data Product Publisher** | Обязательный для аналитики | Публикация аналитического продукта в lakehouse с контрактом и SLA: владелец, схема, freshness, quality-тесты, lineage. Только агрегированные факты и идентификаторы — никаких медданных и лишних PII |
| **ACL Adapter**            | Обязательный при легаси    | Изоляция легаси-форматов (Camel/DWH) от доменной модели: маппинг версионируется, ошибки наблюдаемы, бизнес-логика в DWH не добавляется, адаптер имеет срок вывода                                    |

Два правила, которые не видны из состава компонентов: **модели не разделяются** — «Пациент», «Клиент»,
«Счёт» в разных доменах разные; **сначала контракт** — событие и API описываются контрактом до
реализации, контракт проходит contract-тесты и регистрируется в каталоге.

## 4. Биллинг и расчёты (Billing & Settlement)

### 4.1. Почему выбран Billing

Billing участвует в пилоте (финансовые расчёты), переносит значительную легаси-логику из DWH,
публикует и потребляет события, а его финансовые инварианты (суммы, НДС, закрытие периода) делают
ошибку видимой бизнесу. Соответствие контейнеров целевой архитектуры доменам Task4 — в
[`c4-container.md`](c4-container.md), таблица «Контейнер ↔ bounded context».

### 4.2. Компонентная схема

Схема: [`billing.drawio`](billing.drawio).

### 4.3. Компоненты Billing

| Компонент                    | Элемент шаблона                | Обязанность и правила                                                                                                                                                                                                               |
| ---------------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Billing API**              | Domain API                     | Синхронные команды бэк-офиса и внутренних систем домена: выставить счёт, получить состояние, запросить закрытие периода. Только внутри домена; идемпотентные команды, OpenAPI, авторизация OPA                                      |
| **Billing Store**            | Domain Store                   | PostgreSQL: счета, использование ИИ, расчёты, outbox, проекции. Пишет только Billing, чужие БД не читаются. PITR, шифрование, резервное копирование                                                                                 |
| **Tariff Store**             | Domain Store (read model)      | Справочники услуг, клиник, договоров и налоговых ставок; версии тарифных соглашений. Наполняется через ACL Adapter (волна W0), версионируется, прямых чтений DWH нет                                                                |
| **Tariff Engine**            | Domain Model                   | Расчёт цены: соглашения, пакеты, скидки, приоритет правил, НДС и округление. Результат детерминирован, порядок правил явный, версия соглашения фиксируется; тесты на конфликт правил (W1)                                           |
| **Invoice Service**          | Domain Model                   | Агрегат Invoice: выставление счёта по услугам, позиции, налоги, корректировки. Сумма = позиции + налоги; оплаченный счёт неизменяем, исправление — компенсирующим `billing.invoice.corrected`; обработка идемпотентна по `event_id` |
| **AI Usage Rating**          | Domain Model                   | Агрегат AiUsage: учёт использования ИИ, версия тарифа, сумма к выставлению. Одна запись на анализ, тарификация по зафиксированной версии тарифа; usage становится позицией счёта, а не отдельным платежом                           |
| **Settlement Engine**        | Domain Model                   | Агрегат Settlement: закрытие расчётного периода, сальдо между клиниками и банком. Период закрывается один раз, сальдо = сумма проводок, после закрытия — новая версия, а не правка фактов                                           |
| **Reconciliation Service**   | Domain Model / Process Manager | Сверка расчётов с клиниками и банком, выявление расхождений, правило «четыре глаза». Расхождение > 0,01% блокирует закрытие периода; решение фиксируется в аудите; чужие БД не читаются                                             |
| **Event Handlers**           | Event Handlers                 | Подписки на факты Patient Flow, Diagnostics, AI Analysis, Accounts & Payments, Inventory & Supply и Corporate Finance. Дедупликация по `event_id`, повторные попытки, DLQ                                                           |
| **Outbox Relay + Publisher** | Outbox + Publisher             | Атомарная публикация `billing.*` после изменения агрегата: запись в Billing Store и событие — в одной транзакции, at-least-once, UUIDv7, порядок по `invoice_id`/`settlement_id`                                                    |
| **Data Product Publisher**   | Data Product Publisher         | Публикация `billing_revenue_daily`, `settlements`, `ai_usage_billing` в lakehouse: контракт, SLA, владелец, quality-тесты, lineage. Только агрегированные факты, PII и медданные не публикуются                                     |
| **ACL Adapter**              | ACL Adapter                    | Чтение легаси-данных DWH/Camel и перевод в каноническую модель Billing: волны W0–W4, параллельный прогон, новая бизнес-логика в DWH запрещена. Адаптер выводится после миграции                                                     |

### 4.4. События и взаимодействия

Полный каталог событий и матрица подписок — в
[`../Task4Advanced/event-storming.md`](../Task4Advanced/event-storming.md) и
[`../Task4Advanced/events.md`](../Task4Advanced/events.md); здесь только то, что касается Billing.
Подписки Data Platform (lakehouse) и внешних шлюзов в матрице подписок приведены отдельно: на Context Map
эти потребители не отображаются, так как не являются bounded contexts.

| Направление | Событие                         | Кто обрабатывает                           | Реакция Billing                                                               |
| ----------- | ------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------- |
| Входящее    | `patient.patient.registered`    | Event Handlers                             | Зафиксировать регистрацию пациента; начисление идёт по приёму и исследованию  |
| Входящее    | `patient.appointment.completed` | Invoice Service                            | Счёт по услугам приёма; повтор безопасен по `event_id`                        |
| Входящее    | `diagnostics.study.completed`   | Invoice Service                            | Счёт за исследование по справочнику услуг; повтор безопасен по `event_id`     |
| Входящее    | `ai.analysis.completed`         | AI Usage Rating                            | Учёт использования ИИ и версии тарифа; одна запись на анализ                  |
| Входящее    | `payments.payment.received`     | Invoice Service                            | Счёт отмечен оплаченным, связан `payment_id`; повтор не создаёт второй платёж |
| Входящее    | `inventory.goods.received`      | Reconciliation Service / Settlement Engine | Факт поставки учтён для сверки периода (W3)                                   |
| Входящее    | `finance.period.close.started`  | Event Handlers                             | Корректировки периода заморожены; уведомление, а не контракт модели           |
| Исходящее   | `billing.invoice.issued`        | Accounts & Payments, Corporate Finance     | Ожидание оплаты, дебиторская задолженность                                    |
| Исходящее   | `billing.invoice.paid`          | Corporate Finance, Data Platform           | Факт выручки; закрытие счёта                                                  |
| Исходящее   | `billing.invoice.corrected`     | Accounts & Payments, Corporate Finance     | Компенсирующая корректировка без изменения прошлых событий                    |
| Исходящее   | `billing.settlement.closed`     | Corporate Finance                          | Закрытие расчётного периода                                                   |
| Исходящее   | `billing.ai_usage.recorded`     | Corporate Finance, Data Platform           | Монетизация ИИ и выручка по ИИ-услугам                                        |

Billing и Accounts & Payments образуют два встречных потока фактов: Billing публикует
`billing.invoice.issued`, Accounts — `payments.payment.received`, после чего Billing публикует
`billing.invoice.paid`. Это не цикл моделей: каждый домен владеет своим контрактом и не читает БД другого.

### 4.5. Перенос легаси-логики

Правило восстанавливается в домене, а не копируется как хранимая процедура: ACL Adapter читает
легаси-данные и переводит их в каноническую модель Billing. Волны переноса — W0 справочники в Tariff
Store, W1 тарификация, W2 начисление, W3 деньги и сверка, W4 отчётность заменяется data products;
порядок, критерии и реестр правил — в
[`../Task4Advanced/dwh-to-billing-rules.md`](../Task4Advanced/dwh-to-billing-rules.md). Старый и новый
расчёт сверяются на исторических периодах, расхождение агрегатов — не более 0,01%, переключение чтения
— после двух чистых прогонов; dual-write запрещён, пишет одна система (мера A1 в
[`risk-management-plan.md`](risk-management-plan.md)). Новых правил в DWH не появляется: DWH переводится
в read-only по доменам, затем в архив.

## 5. Масштабирование и вывод легаси

Таблица показывает, как меняются компоненты по этапам трансформации; она дополняет эволюцию контейнеров
в [`c4-container.md`](c4-container.md) и синхронизирована с этапами 0–6 / 6–18 / 18–36 месяцев и
[`../Task5Advanced/roadmap.md`](../Task5Advanced/roadmap.md) §2. Ключевые точки привязки: фундамент
Data Platform — этап 0 роадмапа; полный lakehouse, портал v1, потоковые витрины и интеграция
фарма-партнёров с телеметрией оборудования — этап 2 (6–18 мес); новые регионы (2–3) с локализацией
ПДн и расширение круга партнёров — этап 3 (18–36 мес).

| Зона                 | 0–6 мес (пилот)                                                                                  | 6–18 мес (масштабирование)                                                               | 18–36 мес (доменная аналитика)                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Портал**           | Прототип каталога и конструктора для 20–30 пользователей                                         | Портал v1: все компоненты, ABAC, семантический слой, аудит, экспорт                      | Мультирегиональный портал, расширенные data products, cost guard и квоты; единый каталог регионов |
| **Event Platform**   | Kafka, Schema Registry, outbox, DLQ, базовое governance                                          | Kafka Connect CDC, ACL Adapters, расширенное governance, контракты новых источников      | Региональные кластеры, полная событийная модель, вывод ACL-адаптеров; SLO по всем доменам         |
| **Доменные сервисы** | Billing (W0–W2) и Patient Flow; шаблон проверен на пилоте                                        | Billing (W3–W4), Lending, Inventory & Supply, Corporate Finance; новые домены по шаблону | Все направления на шаблоне; data products по всем регионам, монетизация ИИ                        |
| **Источники**        | DWH — источник истины, Camel — существующий мост; фундамент lakehouse (Object Storage + Iceberg) | Фарма-партнёры и Device Telemetry Gateway (MQTT → Kafka), CDC из DWH                     | Локальные источники регионов через адаптеры; легаси-мосты вне критического пути                   |

Правила масштабирования:

1. **Новый домен** — новый экземпляр шаблона раздела 3: API, стор, outbox, обработчики, data products,
   при необходимости ACL. Существующие домены, портал и Event Platform не меняются: они работают с
   контрактами и data products, поэтому новое направление не требует новой бизнес-логики в DWH.
2. **Новый источник** — адаптер (ACL или Device Telemetry Gateway) и контракт события; новые таблицы DWH
   не создаются.
3. **Новый регион** — отдельный контур портала, Event Platform и lakehouse с учётом локальных требований
   к ПДн; глобальные справочники реплицируются отдельно.
4. **Вывод легаси** — поэтапно: параллельный прогон → read-only → архив/отключение. У каждого моста есть
   владелец, метрики использования и критерий вывода; график — в [`c4-container.md`](c4-container.md) и
   [`risk-management-plan.md`](risk-management-plan.md).
